# The Contractor — CLAUDE.md

FS25 mod. Full design context lives in `BRIEF.md`; work is tracked ticket-by-ticket in `tickets/` (see `tickets/README.md` for the backlog, phase ordering, and cross-cutting decisions agreed during the initial grilling session). Always check a ticket's `Status` and `## Outcome` section before assuming its acceptance criteria describe the current code — outcomes note deviations.

## Sibling references

- `../FS25_RedTape` — the user's other FS25 mod; the house-style template this mod's conventions (below) are lifted from. When in doubt about "how would this shop do X," check RedTape first.
- `../Reference/FS25_Lua` — decompiled base-game Lua, for looking up vanilla function signatures (`Farm:getBalance`, `FSBaseMission:addMoney`, `FarmManager`, etc.) rather than guessing them.

## Conventions (established, don't relitigate)

- **State is farm-scoped**, not per-player — e.g. `Company.lua`'s `companyNames[farmId]` (one company per farm, 1:1 — presence of a name in that table IS "has a company," don't add a redundant boolean flag alongside it). In single-player the player is always farm 1; multiplayer has multiple farms, so never assume "the" farm — always key off the relevant `farmId` (usually `g_currentMission:getFarmId()` for the local player's farm). No separate business ledger: the contractor business spends/earns from the farm's existing money via `g_currentMission:addMoney(amount, farmId, moneyType, addChange, forceShowChange)`. Tax is explicitly out of scope (another mod handles it).
- **Multiplayer is a hard requirement, not deferred.** See `src/events/README.md` for the full event-authoring convention (event file shape, the `TCInitialClientStateEvent` aggregate pattern, and three gotchas: no single-player broadcast loopback, never send raw node objects over the wire, defer object resolution during initial client state). Every new piece of mutable state needs a reactive event, following `src/events/TCCreateCompanyEvent.lua` as the template for "client requests, server validates + applies, broadcasts to other clients."
- **Save/load**: one `TheContractor.xml` per savegame (`TheContractor.SaveKey = "TheContractor"`), legacy XML API (`getXMLInt`/`setXMLInt`/`getXMLString`/`setXMLString`/`hasXMLProperty`, not the newer `xmlFile:getInt` object API). Each subsystem under `src/business/` owns its own `loadFromXMLFile(xmlFile)`/`saveToXmlFile(xmlFile)` pair, delegated into from `main.lua`. New subsystems must also grow `writeInitialClientState`/`readInitialClientState` stubs even if empty, so `TCInitialClientStateEvent` has something to call.
- **Menu**: one top-level "Contractor" icon injected into `g_inGameMenu` via `MenuContractor.registerInIngameMenu` (adapted from `RedTape.addIngameMenuPage`, itself credited to Courseplay) — there is no declarative XML/config way to add a top-level page, it's direct manipulation of the live `g_inGameMenu` singleton at map-load time. Tabs are a single `TabbedMenuFrameElement` subclass (`MenuContractor`) with a `subCategoryPaging` widget; add tab *content* gating (like the "create a company first" lock) via `setText`/`setVisible` on already-registered controls, not by removing tabs — reshuffling `subCategoryTabs`/`subCategoryPaging` indices at runtime is fragile.
- **Menu enable predicate stays always-`true`.** The top-level Contractor page is never gated on having a company — see `tickets/006-company-activation.md`'s Outcome for why (chicken-and-egg: "Create Company" has to be reachable before a company exists). Actions is tab 1 (first/default) for the same reason. Don't "fix" this without re-reading that reasoning.
- **Menu action buttons go in the bottom button bar, not in-page `Button` GUI elements.** Follow `MenuRedTape`'s pattern (its Grants/Schemes tabs): build an entry (`{ inputAction = InputAction.MENU_ACTIVATE, text = ..., callback = ... }`), add it to `self.menuButtonInfo[category]`, and override `getMenuButtonInfo()` if the button should only appear conditionally (see `MenuContractor:getMenuButtonInfo` — the Create Company button only appears while the farm has no company). Call `self:setMenuButtonInfoDirty()` after any state change that should update the bar immediately. **The bar has a fixed number of slots (six, counting Back/Next/Prev) and silently drops any entries past them**, so a tab with more actions than fit groups them behind one button that opens an `OptionDialog` (see `MenuContractor:onClickManageWorker`, 066).
- **Menu visuals use the panel kit in `src/gui/guiProfiles.xml`** (see `tickets/043-menu-visual-polish.md`): details go in a `tc_panel` card with `tc_sectionTitle` + `tc_divider` and label/value rows in a `tc_detailRows` BoxLayout (give it an id and call `invalidateLayout()` every time it's filled — the setup-time layout leaves rows unplaced, so they don't render at all otherwise); status goes in a chip via `MenuContractor`'s `setChip(chip, chipText, text, tone)`, not `setTextColor`. `tc_tableListItem` is transparent — **every ListItem template must start with `<RoundCorner profile="tc_tableRowSurface"/>` and `<Bitmap profile="tc_tableRowAccent"/>`**, or its rows have no background and no visible selection. Colours live in the `<Presets>` there; element-level `with=` is ignored, so anchors must come from profiles.
- **Naming/text-entry prompts** use `TextInputDialog.show(callback, target, defaultText, dialogPrompt, imePrompt, maxCharacters, confirmText)`; the callback receives `(target, text, clickOk)`. Use `InfoDialog.show(text)` for a blocking one-button message (e.g. "can't afford this") and `YesNoDialog.show(callback, target, text)` for a plain confirm — see `MenuContractor:onClickCreateCompany` for the funds-check-then-prompt pattern. In our own dialogs (`TCAdvertisingDialog` and the like), **never store state in `self.name`**: it's the GUI name `loadGui` gave the dialog, and `close()` closes by it. Overwrite it and Back/close quietly do nothing (066).
- **Money types — full checklist, every time.** Registering a custom `MoneyType` takes four steps, not two; skipping the last one silently breaks the in-game Finances screen for that stat (see `tickets/006-company-activation.md` and `tickets/012-advertising-system.md` Outcomes — this bit both `tcCompanyCreation` and `tcAdvertising` before being caught and fixed as a follow-up):
  1. `FinanceStats.statNames`/`statNameToIndex` entry, at module scope (runs once) — following `RTPolicySystem`'s pattern.
  2. `MoneyType.register(name, l10nKey)` + `MoneyType.LAST_ID = MoneyType.LAST_ID + 1`, inside the subsystem's `.new()` (runs once per `loadMap`, matching RedTape's own — mildly wasteful across multiple save loads in one session, but that's the established convention, not a bug to fix unilaterally).
  3. The `l10nKey` text itself in `languages/l10n_en.xml` (e.g. `tc_moneyType_<name>`).
  4. **A second l10n entry, `finance_<name>`, plus a whitelist entry in `src/extensions/TCI18NExtension.lua`.** The Finances screen's row label comes from base-game `FinanceStats.new()` calling `g_i18n:getText("finance_" .. statName)` with no `modEnv` — it only ever checks I18N's global/unscoped text table, never a mod's own l10n file, so a mod-registered stat renders as a missing-text placeholder there without this. `TCI18NExtension` (same fix `FS25_RedTape/src/extensions/I18NExtension.lua` uses) patches `I18N:getText` to force our mod's env onto a whitelist of our own keys when no `modEnv` was given — add both the `l10nKey` from step 3 and the new `finance_<name>` key to `TCI18NExtension.theContractorTexts`.
- **Icons**: `images/menuIcon.dds` is a placeholder the user swaps out from time to time — don't spend effort designing real icons. **Its pixel size matters**: `MenuContractor.registerInIngameMenu`'s `iconImageSize` param must match the actual `.dds` dimensions (passed through to `GuiUtils.getUVs(uvs, iconImageSize)`), since `GuiUtils.getUVs` assumes a 1024x1024 atlas if you omit it — RedTape's icon happens to be 1024x1024 so it can skip the param, `FS25_ImprovedControlsMenu`'s 128x128 icon cannot. If the user swaps the icon file, check its size and update both `iconImageSize` and the `uvs` rect in `main.lua`'s call.
- **Company logo**: the Overview's company card shows `TCCompanyLogo.getFilename()` (`src/util/TCCompanyLogo.lua`): the player's `logo.dds`, else `logo.png` (PNG works for the logo and the signs, with vanilla's performance warnings; a DDS wins over a same-named PNG) in `modSettings/FS25_TheContractor/savegame<N>/` (the current save's slot, `missionInfo.savegameIndex`; never on a joining client, whose index is 0), else `modSettings/FS25_TheContractor/`, else `images/defaultLogo.dds` (a 512x512 placeholder the user swaps out; the box is a 204x204 square, and custom logos must be square with sides a multiple of 4). Local only by design: nothing saved or streamed, every machine reads its own modSettings. The sign placeables (084's freestanding Company Sign `xml/logoSign.xml`, 087's Wall Signs `xml/wallSign[Large]<1|3|6>m.xml`, one `tcLogoSign` type, `src/placeables/PlaceableTCLogoSign.lua`) show the same file on their `<logoSign><face>` shapes by swapping their material's diffuse map at load (`setMaterialDiffuseMapFromFile`, as vanilla's pallets do): the player's logo only on their own farm's signs (and while placing one), `TCCompanyLogo.getDefaultFilename()` on anyone else's, redone on an owner or player-farm change. Every sign has 085's `tcSignDesign` configuration, whose options `TCSignDesignConfigurationItem.postLoad` builds from the `.dds`/`.png` images in `modSettings/.../signs/` (`TCSignImages`, saved by file name), like vanilla's tree sapling configuration. Designs are single-player only: configurations sync by index and each machine reads its own folder, so in multiplayer `getDesigns` returns none, the logo is the only option on every machine, and the construction menu shows no picker (087 merged 085's separate Custom Sign into this). Wall sign heights are baked into each i3d (FS25_placeableWallLights' approach); a new sign i3d comes from `docs/tools/` (see `docs/logo-sign-i3d.md`). `TCCompanyLogo.createSettingsFolder` writes one `README.txt` covering both, rewritten on every load (it is the mod's, not the player's to edit).
- **Settings** (048) live in `src/business/Settings.lua` (`tc.Settings`), shown in the vanilla Settings page by `src/gui/TCSettingsMenu.lua` and synced by `TCSettingsEvent`. They are server-wide, not farm-scoped. Add one with a `DEFINITIONS` entry, its id in `ITEMS`, and `tc_setting_<id>`/`tc_toolTip_<id>` l10n keys. Save/load, MP sync and the menu control all follow from `ITEMS`. A per-player display preference goes in `LOCAL_ITEMS` instead (086, `showParkingSlots`): same menu section, open to everyone, never synced, saved in `modSettings/FS25_TheContractor/localSettings.xml` (`loadLocalFile`/`setLocal`), with an optional `onChanged` in its definition.
- **Fixed business costs follow the job pay setting.** Job pay is far above real UK rates (047), so overheads, claims and the excess, the solicitor's fee, training and fines are written as 1x UK constants and charged through `tc.Settings:scaleCost(amount)`: `COST_BASELINE` (5) x UK at the default 100% job pay rate, in proportion otherwise. A new fixed cost goes through `scaleCost` too, and so does any amount shown for it. Wages, bonuses, notice/redundancy pay and office staff's salaries are pay and stay at 1x UK. Salaries (and the notice/redundancy pay worked out from them) are stored as full-month figures and scaled for short months by `TheContractorStaff.scalePay` (60% at 1 day per period, full pay from 5, read live). Anything that charges or shows a salary goes through it, and an inbox arg showing one uses `$pay_<number>`, not `$money_`. Bonuses are fixed amounts and aren't scaled.
- **FS25_EconomyScale** (`src/util/TCEconomyScale.lua`): that mod scales every vanilla price getter by one factor. Our own prices come from constants, so we apply its factor (`g_currentMission.EconomyScale.factor`, 1 without the mod) ourselves, live: in `TheContractorJob:getPrice`/`getOfferedPrice`, `scaleCost` and `scalePay` (and `getWeeklyPay`), so anything going through those is covered already. A new fixed amount that goes through none of them (like the company creation cost, advertising, bonuses) goes through `TCEconomyScale.scale` when it's charged and shown. Store amounts unscaled, as salaries are. **Never scale anything read from a vanilla price getter** (`getSellPrice`, `getPrice`, `getCostPerLiter`, repair prices): EconomyScale already has, so insurance's fleet-value premium (`unscaled = true`), stolen vehicle values and job diesel stay as they are. Bonuses keep their base amount for the choice, the event and the morale effect (`TheContractorMorale.getBonusCost` is what's paid). Jobs store `basePrice`/`baseOfferedPrice` without the factor (generation, saves and the stream all use base amounts). Read them only through `getPrice`/`getOfferedPrice`, and set a price the player typed with `setPrice` (counter offers are judged at the current level). So an unpaid job follows the factor, like a vanilla contract's reward does under EconomyScale. **History is fixed**: `paymentAmount` is taken at completion, and invoices, the logbook and Finances figures keep the amounts they had.
- **Job payment goes through `tc.Finances`** (049, `src/business/Finances.lua`): `Jobs:completeJob` calls `Finances:invoiceJob`, which invoices (paid later on the daily tick) or pays at once if the `lateInvoices` setting is off. Invoices' hidden `paymentDay`/`isBadDebt`/`isLate` are server-only, never streamed. Anything that charges wages should also call `Finances:recordWages` so the Finances tab's year-to-date figures stay right; later costs (051) feed `getForecast`.
- **Asking the player something goes through Inbox messages** (050, `src/business/Inbox.lua`, `tc.Inbox`): register a kind with `registerMessageKind(kind, { onAction, onExpire, chipKey, chipTone, getConfirmText?, getArgs? })` (`getConfirmText(message, actionKey)` returns text for a Yes/No before the action is sent, or nil; `getArgs(message)` returns the args to render with, worked out live on each client, as 089's "who else is off" list is) on every machine at load, then `postMessage(...)` on the server. Title/body are l10n keys + plain-value args (rendered per client; a `$l10n_<key>` string arg is translated, `$money_<number>` formatted as money, `$pay_<number>` formatted as money after `scalePay`, `$days_<first>_<last>` as a date range), max 3 actions, none means a single Dismiss.
- **Recurring costs go through `tc.Overheads`** (051, `src/business/Overheads.lua`): register `{ key, l10nKey, mandatory, isRequired?, annualCost(farmId), descriptionAmounts? }` with `registerOverhead` on every machine at load, plus `tc_overhead_<key>` and `tc_overhead_<key>_desc` l10n keys. The description is run through `string.format` with `descriptionAmounts` (money constants, formatted in the player's currency), so put prices in it as `%s`, never bare numbers, and write a literal percent sign as `%%`. Billing (annual 12% off vs monthly), renewals, renewal-notice inbox messages, the Finances tab's Overheads view, the forecast and MP/save all follow. Costs are written at 1x UK and `getAnnualCost` scales them (see the fixed-costs bullet below). Read a farm's cover with `isActive(farmId, key)`. An optional overhead priced up for claims can add `getRenewalLoading(farmId)` → `claimCount, loadingPercent` so the renewal notice explains it (052's public liability, registered from `src/business/Claims.lua`).
- **Worker names** (082, `src/util/TCNames.lua`): every new name goes through `TheContractorStaff.generateName(gender)`, which reads the `nameStyle` setting (`Settings:getNameStyle()`, a style key or a mix: `european`, `all`). First name and surname always come from the same style; a surname can be `{ male, female }` (Polish). The setting saves the option's number, so a new style goes on the end of `TheContractorSettings.NAME_STYLES`, plus a `TCNames.STYLES` entry, a `STYLE_ORDER` entry and a `tc_nameStyle_<key>` l10n key. Existing names never change.
- **Trade association and legal cover** (053, `src/business/Association.lua`, `tc.Association`) are two optional overheads with no state of their own. Read them with `isMember(farmId)`/`hasLegalCover(farmId)`. Member perks go through it: `getCertificationDiscount(farmId)` (0.25 for members, else 0; non-members can still certify at full price) for 054, and `getReputationBonus`, which is already applied in `Jobs:calculateReputationReward`. Pursuing an overdue invoice is in `Finances` (`requestPursuit`, status `pursuing`).
- **Certificates and training** (054, `src/business/Training.lua`, `tc.Training`): `worker.certifications` is a set. A job type that needs one names it as `certification` in `JobGeneration.JOB_TYPES` (herbicide → `"spraying"`), and `Allocation:previewWorkerCapability` blocks uncertified workers. Add a certificate as a `TheContractorTraining.CERTIFICATIONS` entry (skill, readySkill, courseCost, retakeCost, courseDays) plus a `tc_cert_<key>` l10n key. Training is `STATUS.TRAINING` on monotonic days, booked from tomorrow at the earliest (`BOOKING_LEAD_DAYS = 1`, a holiday only moving it if the booking would run into it), and a missed day slides the rest of the schedule back. Every course length (054, 090's office Train, 092's trades) goes through `TheContractorTraining.scaleDays` (never longer than a month), and the assessment's wait through `getAssessmentGap`. The state lives on the worker and is saved/streamed with it (`TheContractorTraining.writeState`/`writeXML`). `declinedRequests` is recorded for 056's morale and nothing reads it yet.
- **Health and safety programme** (055, `src/business/HealthSafety.lua`, `tc.HealthSafety`) is an optional overhead (250 per worker a year) with no state of its own. Sickness reads it live: `getSicknessMultiplier(farmId)`/`getExtraDayChance(farmId)` in `Staff:updateSickness`/`makeWorkerSick`. Every new sickness goes through `Staff:makeWorkerSick`, which also runs the no-programme inspection roll (fine under `tcFines`, recorded with `Finances:recordFines`).
- **Staff morale** (056, `src/business/Morale.lua`, `tc.Morale`): `worker.morale` 0-100 moves by bumps (`Morale:adjust(farmId, workers, delta)`, one broadcast) and a monthly drift toward a workload target. Read its effects through `TheContractorMorale.getRetirementMultiplier`/`getGrowthMultiplier`/`getJobQualityMultiplier`; something new that should upset or please staff calls `adjust`. Bonuses are pay (`TC_WAGES` + `Finances:recordWages`). A worker who's handed in notice is `worker:isLeaving()` (`leavesAtPeriod`, with `isQuitting` telling a quit from a retirement); both leave through `Staff:announceLeaving`/`retireWorker`. `releaseWorker` charges `TheContractorStaff.getReleaseCost(worker)` (UK notice and redundancy pay), computed the same way on every machine so the confirm dialog can show it. Service is counted from `worker.hiredPeriod` (a period index, not a day).
- **Office staff** (057, 090, `src/business/Office.lua`, `tc.Office`): the office administrator is a per-farm role (`membersByFarm[farmId][role]`, the only one since 098 made the storekeeper a workshop trade; an old save's office storekeeper is dropped on load), not a worker: no roster, allocation, skills, growth, morale, sickness or holidays. They are people, though: a name, gender and look, a row at the bottom of the Staff tab's roster (hired, released and managed there) with the shared portrait, and a place on standing spots. Their ids come from `Staff:takeWorkerId()`, so they never clash with a worker's, and editing goes through the worker path (`Staff:getEditablePerson`). Anything that pays or counts employees should use `Staff:getPayroll(farmId)` (roster salaries plus the office, which feeds pension and the wage bill) or `Staff:getHeadcount(farmId)` (used by employer's liability), not just the roster. `getTotalSalary`/`getRoster` stay field-staff only. Credit control is `hasAdministrator(farmId)`, and invoice rolls read it through `getDelayWeights`/`getBadDebtChance`/`getLatePayerChance`. It has a level 1–3 with a fixed salary per level, raised by Train (a `scaleCost` course, a few days away). Levels only matter to FS25_AdvancedDamageSystem's own workshop, where `TCADSWorkshop` (`src/util/TCADSWorkshop.lua`, the `TCADSStock` pattern, checked against `../FS25_AdvancedDamageSystem-dev` 0.10.0.6, commit `2901e04`) registers us as its staff provider: the administrator is its receptionist. Train is only offered while `TCADSWorkshop.isActive()`. Anything that changes who ADS should see calls `TCADSWorkshop.refresh(farmId)` (Office's `commit` already does).
- **ADS workshop trades** (091, `src/business/Workshop.lua`, `TheContractorWorkshop`, no state of its own): `worker.adsSkills` (`{ mechanic|diagnostician|bodyworker|storekeeper = 1-3 }`, at most two; the storekeeper was an office role until 098, and ADS ignores one while the workshop has no parts storage, which the Staff tab's workshop note says (`NEEDS_PARTS_STORAGE`, `TCADSWorkshop.hasPartsStorage`); these and `receptionist` are ADS's role ids, which its API and our saves use, but ADS shows the diagnostician as "Electrician" and the receptionist as "Advisor", so our l10n (`tc_office_adsRole_<id>`) and the console (`TheContractorWorkshop.findRole`, which also takes `electrician`) do too) and `worker.workshopRole` (the trade they're ticked into, nil otherwise) live on the worker: saved, streamed with it, and changed only through `TCWorkerWorkshopEvent` (`setRole` on the server, one worker per role per farm, ticking someone into a taken role moves the other out; `setSkills` for the console). Skills are only rolled for candidates while `TCADSWorkshop.isActive()`, but once a worker has them they always count toward market value (`getSalary`'s `adsSkills`), whether ADS is using them or not. ADS sees a ticked worker as `available` only while idle (`getADSStatus`: assigned, driving and cooldown are `working`). Allocation still takes them and only warns. The Staff tab's ADS column, Workshop section and Manage entries all hide without ADS. **Trade courses** (092): Manage → Workshop training books a worker on `COURSES` (learn a trade at level 1, or the next level), a 054 booking with `trainingCert = "workshop_<role>"` (`getCourseKey`/`getCourseRole`), no assessment, the level raised by `completeCourse` on the last course day; check `getCourseProblem` (or `getLevelProblem` for the limits alone), price with `getCoursePrice`. Anything reading `trainingCert` must allow for a trade course and `assessmentDay == nil`.
- **Pay reviews** (058, `src/business/PayReviews.lua`, `tc.PayReviews`): a hired worker's `worker.salary` is their real pay. It's fixed at hire and only raised (never cut), through `PayReviews:setPay` (an inbox pay review or the Staff tab's Pay rise). Growth only raises their market value. Read that live with `TheContractorPayReviews.getMarketValue(worker)` (`Staff.getSalary(stats)`, still a candidate's asking salary). `worker.expectedSalary` is rolled on hire anniversaries with a tenure discount, and pay against it shifts 056's drift target (`getMoraleTargetShift`, folded into `TheContractorMorale.getTarget`). Anything that takes a worker off the roster should also call `PayReviews:removeMessagesFor`.
- **Vehicle references** (`src/util/TCVehicleIds.lua`, the UsedEquipmentYards pattern): in memory and on the wire a vehicle is its network object id (`NetworkUtil.getObjectId`/`getObject`). Object ids are handed out afresh on every load, so **the save stores `vehicle:getUniqueId()`**, never an object id. Vehicles load after `loadMap`, so a subsystem keeps its loaded uniqueIds in a holding field (e.g. `job.savedEquipmentUniqueIds`) and converts them in its own `resolveSavedVehicles`, which you add to `TheContractor:resolveSavedVehicles` (runs once: first update, a client joining, or a save, whichever comes first). A vehicle that's gone just drops out. On a client, anything that acts on a vehicle has to wait until it has streamed in and synchronised (see `TCEquipmentVisibility` and `src/events/README.md`).
- **Logbook** (060, `src/business/Logbook.lua`, `tc.Logbook`) records snapshots as things happen: a job entry on completion or miss, and per-vehicle entries for job use, staff drivers and players. Vehicle records are keyed by object id like everything else, and a vehicle's history goes when it's sold (job entries copy machine names in). Condition goes through `TCVehicleCondition.capture`, which records whether it's a vanilla snapshot (damage, paint, repair price) or an ADS one. **An ADS snapshot holds only what the player knows** (099, at the ADS author's request): the last inspection's condition (`getLastInspectedCondition`: value, exact, stale; shown through ADS's own `ADS_Utils.formatCondition`, via `formatKnownCondition`) and the faults with `isVisible`. ADS's live `getConditionLevel()` and hidden faults are fine for our own maths (job quality, road accidents) but never go on screen, and which job caused a fault isn't told (`faultCaused` is kept, never shown; the logbook shows `hasFoundFault`). ADS wear cost is 0 until ADS has a repair cost function (a TODO in `getWearCost`). ADS globals are reached through `TheContractorDrivers.getModEnv("FS25_AdvancedDamageSystem")`, checked against `refs/FS25_AdvancedDamageSystem` (0.10.0.0); vehicle methods like `addBreakdown` need no env. Show it with `getChangeRows`/`getStateRows`, never by assuming one model. Something new that should appear in a job's record (a cost, a time) gets stored on the server's pending data for that job (`onWorkStarted`/`onArrived`/`onSuppliesLoaded`), then copied into the entry by `buildJobEntry`.
- **Parking** (062): equipment back from a job is never revealed where it stood. It goes to the parking return queue, `tc.Parking` (`src/business/Parking.lua`), with `returnVehicles(farmId, vehicleIds)` (or `returnHiddenVehicles` when some of it may never have left the yard). The queue unhitches each piece, keeps it hidden and locked, and parks one at a time in a free Parking Slot owned by the farm. `TCParking` (`src/util/TCParking.lua`) does the spot-finding and shop placement. A vehicle is in a cooldown or the queue, never both: anything that takes a machine out again (a cooldown starting, a dispatch setting off) calls `removeVehicles` first. Parking Slots (`src/placeables/PlaceableTCParkingSlot.lua`) come in three widths, all 9 m long: `parkingSlot` (4 m), `parkingSlotMedium` (12 m) and `parkingSlotLarge` (24 m), each in two types set by the xml's `parkingSlot#slotType`: `vehicle` (those three names) and `implement` (`parkingSlotImplement`, `parkingSlotImplementMedium`, `parkingSlotImplementLarge`). A third type, `harvester`, has one 8 m x 13.5 m slot (`parkingSlotHarvester`). `findSpot` only puts a self-propelled harvester (`spec_drivable` and `spec_combine`) in a harvester slot, any other drivable machine in a vehicle slot and anything else (headers and trailed harvesters too) in an implement slot (`PlaceableTCParkingSlot.getSlotTypeFor`); there's no fallback to another type. A placed slot can also carry a **filter** (086): some store categories (`TCEquipmentClass.getCategory`, a vehicle's primary one) and/or some of the farm's machines, set from a prompt standing in the slot (`TCParkingSlotActivatable` → `TCParkingSlotDialog` → `TCParkingSlotFilterEvent`). It's the slot's own state, saved in vanilla's `placeables.xml` through the spec's `saveToXMLFile`/`loadFromXMLFile` (vanilla's `XMLFile` object, so not the legacy API) and streamed with the placeable, with machines by uniqueId in the save and resolved in `TCParking.resolveSavedVehicles`. `findSpot` goes through `TCParking.getSlotsFor`: slots naming the vehicle, then those taking its category, then unfiltered ones; a filter only narrows, so anything its own slots can't hold falls back to an unfiltered one. Each is an `xml/<name>.xml` store item registered in `modDesc.xml` and a store icon at `images/store/<name>.dds`. A vehicle slot and an implement slot of the same size share `i3d/parkingSlot<Size>.i3d`; the harvester slot has its own `i3d/parkingSlotHarvester.i3d`. They sit in our own "Contractor" tab of the construction menu's Buildings category, declared in `modDesc.xml`'s `<constructionCategories>`; point any future placeable's `<brush><tab>` at `contractor` too. Their terrain-decal visuals show while the construction menu is open (`TCParking.installConstructionScreenHook`), and everywhere while the player's local `showParkingSlots` setting is on (086: `TCParking.updateVisuals`/`areSlotsShown`, toggled by the `TC_TOGGLE_PARKING_SLOTS` key action, right ctrl + P by default, registered from `PlayerInputComponent.registerGlobalPlayerActionEvents` as FS25_MoistureSystem does). Standing spots still only show in the construction menu. Hooking `ConstructionScreen.onOpen`/`onClose` on the class does nothing, because the screen element holds copies of them. Opening raises the element's `onOpenCallback` (`g_gui.screens[ConstructionScreen]`). Closing usually doesn't: the screen closes itself with `self:changeScreen(nil)`, which calls `onClose` straight on the controller, so `g_constructionScreen.onClose` is wrapped as well as the element's `onCloseCallback`. Plain `setVisibility` is enough for the decals. Selecting a slot to sell it doesn't rely on its thin pick box alone, since slots don't level the ground and terrain can cover it: `TCParking.getHitPlaceable` wraps `GuiTopDownCursor.getHitPlaceable` so a terrain hit inside a slot's rectangle selects it. Vanilla owns their saving, sync and ownership. `TCParking.findSpot` works on any rectangle, so a bigger parking area is only a new i3d/xml. The i3ds are GIANTS Editor files: see `docs/parking-slot-i3d.md` for how they were generated, the node order the xmls rely on, and the reminder that a regenerated (inline-mesh) i3d must be re-saved in GE to get its binary `.shapes` file.

- **Random events** (068, `src/business/RandomEvents.lua`, `tc.RandomEvents`): an event type registers on every machine in `loadMap` (before the save loads) with `registerEventType(key, { l10nKey, ratePerPeriod(farmId), canTrigger(farmId), cooldownPeriods, stages })`. Rates are **per month** and the daily roll divides by days per period; stage waits are `delayPeriods = { min, max }` in months, turned into days (at least 1). Never write an event's odds or waits in days. An event that should happen at a time of day adds `triggerHours = { startHour, endHour }` (078): still rolled at midnight, then held server-side (saved) until a random hour in the window, firing late rather than never if the hour's skipped. Diesel theft (078, `src/business/DieselTheft.lua`, no state, no cooldown) uses it: the farm's fullest diesel storage drained or a few of 069's eligible machines siphoned, litres just gone (063's noStock hold follows). An inbox arg showing litres uses `$volume_<number>`. `canTrigger` returns the incident's starting `data` (flat number/string/boolean values only: that's what gets saved and synced), or nil. A stage's `run(incident)` returns nil (next), a stage key, `DONE` or `WAIT` (resume later with `goToStage`). Messages, notices and money come from the event type's own stages. Off/Rare/Normal is the `randomEvents` setting; `tcCompany event <type> [details]` forces one. **An event type's console needs go on its definition, never a new `tcCompany` subcommand** (083): `console = { prepareTrigger(farmId, details), clearTrigger(), outcomes = { ... }, setOutcome(outcome) }` gives it `tcCompany event <type> <details>` (a worker, a story) and `tcCompany outcome <type> <outcome>` (forcing how the next one comes out, kept server-side in a `forced...` field the event reads once and clears).
- **Vehicle theft** (069, `src/business/Theft.lua`, `tc.Theft`) is a random event with no state of its own: the stolen vehicle lives in its 068 incident's data (`vehicleId`, plus `vehicleUniqueId` for the save, re-resolved in `Theft:resolveSavedVehicles`). **ADS's anti-theft system** (096, an ADS workshop upgrade only offered while we're loaded) is read with `TheContractorTheft.hasAntiTheft(vehicle)` (`vehicle:hasBreakdown("ANTI_THEFT_SYSTEM")`, nil-checked, so false without ADS): a fitted vehicle counts `ANTI_THEFT_WEIGHT` (0.1) of its theft weight and of a vehicle in the fleet factor, is recovered at `ANTI_THEFT_RECOVERY_CHANCE` (0.95, judged by the incident's `antiTheft`, copied at the theft), and counts `ANTI_THEFT_DISCOUNT` (15%) less of its value in machinery insurance's premium (`getFleetValue` returns the real value, the priced value and the fitted count). Check `tc.Theft:isStolen(vehicleId)` anywhere that lists or uses the farm's vehicles: allocation, `TCVehicleLock` and selling (`Vehicle.getCanBeSold`/`getIsInUse` hooks) already do. A police report that doesn't find it deletes the vehicle there and then (`deleteStolenVehicle`), insured or not; 070's claim stages then run on the value copied into the incident, before the `writtenOff` stage. The stolen inbox message's id is kept (`stolenMessageId`) and taken down at the report.
- **Selling busy equipment**: `TCVehicleLock` hooks `SellVehicleEvent.run` on the server and refuses anything it would lock (a hired-worker job's kit while allocated or in progress, cooldown, the parking queue, stolen) or anything hitched to it, with vanilla's "in use" reply. The check is worked out live, not from the last refresh. Its Tab-cycle lock wraps each vehicle's own `getIsTabbable`; never call `Enterable:setIsTabbable` for a temporary state, because vanilla saves that flag with the vehicle. Never do this by hooking `getIsInUse` for job equipment: our own dispatch's `AIJob:getIsStartable` checks it and would refuse the job's machines.
- **Machinery insurance** (070, `src/business/MachineryInsurance.lua`, `tc.MachineryInsurance`) is an optional overhead with **levels of cover**: a definition can have `levels = { { key, l10nKey, annualCost(farmId), getDescription? } }`, picked in an `OptionDialog` when it's taken out and changed for the next term (`state.level`/`pendingLevel`, saved and streamed with the rest of the state). Its premium is a share of the fleet's value, already a game price, so the definition is `unscaled = true`; the excess is a 1x UK cost and is scaled. Cover is judged on the day of the incident: an insurable event type names its `peril`, stores `getCoverLevel(farmId, peril)` (or "") as `coverLevel` in its incident data, along with `name` and `value`, and puts `getClaimStages(afterStageKey)` in its own stage list (`claim` → `claimSettle`/`claimSettleFast`). A new peril (fire, storm) is a `PERILS` entry plus that, not a new policy. Payouts are `tcInsurancePayout` and `Finances:recordInsurancePayout`; the excess goes through `recordClaims`. A submitted claim has an Overview notice (`claimNoticeId`) until it settles. The level picker lists level names only; the dialog text below shows the highlighted level's price and description, swapped by a temporary `onClickCallback` on vanilla's `OptionDialog.INSTANCE.optionElement`.
- **Joyriders** (072, `src/business/Joyriders.lua`, `tc.Joyriders`) is a random event with no state of its own (incident data `{ fieldId, isOwnField }`): a grass field of an NPC's or the farm's own, never another player's, with no live job and not in winter, is torn up by `TCJoyriderRuts` (`src/util/TCJoyriderRuts.lua`: a pure car-steering path that stops on grid coverage then drives off the field, painted through vanilla's cultivator area, clipped to the field, never `PLOWED`). An NPC's field gets a plow offer, due this month, through `JobGeneration:createJobOnField(farmId, jobType, field, sameMonth)`, which dates and prices a job on a given field without checking its eligibility (`sameMonth` caps the deadline at the month's last day unless it's too late in that day); use it for any other event that causes work. Two server-only, saved job flags: `keepFieldState` (`TCFieldPreparation` leaves the field alone at allocation while it's still grass) and `followOnSow` (`Jobs:completeJob` calls `Joyriders:onJobCompleted`, which offers a grass sow job half the time by setting the field's planned crop to grass, and puts the plan back if grass can't be sown now).
- **Courtesy vehicle** (071, `src/business/CourtesyVehicle.lua`, `tc.CourtesyVehicle`): a level with `courtesyVehicle = true` (comprehensive) lends a similar vehicle from a "not found" police report until settlement. It's spawned with `VehiclePropertyState.MISSION` (no leasing, upkeep or wear, no vanilla sell button), so anything that should skip it can rely on `propertyState == OWNED` (theft eligibility and the insured fleet already do), or ask `isCourtesy(vehicleId)`. Don't hook `getIsInUse` for it: AI jobs and resets refuse a vehicle "in use". Vanilla limits a MISSION vehicle's own work areas to mission fields, so `WorkArea.getIsAccessibleAtWorldPosition` is patched to judge a courtesy vehicle as owned. It lives in the theft incident's data (`courtesyVehicleId`/`courtesyUniqueId`/`courtesyName`) and goes back through the `courtesyReturn`/`courtesyRetry` stages after `writtenOff`, retried daily while it's in use, on a job or in a cooldown. One out on a job is flagged on the Overview's job line (`getDueOnJob`) and collected as the job's equipment comes home: `Parking:returnVehicles` passes everything through `collectDueVehicles` first.
- **Good news** (073, `src/business/GoodNews.lua`, `tc.GoodNews`) is one random event for every story with no mechanics of its own: a reward and an inbox message, nothing else. A story is a `TheContractorGoodNews.STORIES` entry with exactly one of `reputation` (job-equivalents, scaled to the farm's tier by `getReputationReward`) or `money` (1x UK, paid through `scaleCost` under `tcGoodNews` and `Finances:recordGoodNews`), plus `tc_goodNews_<key>_title`/`_body` l10n keys (the body's one `%s` is the amount). A story that needs anything more (a job, an invoice, a worker) is its own event type. The farm's last story is kept server-side (`lastStoryByFarm`, saved) so none comes twice in a row.
- **Job quality and reputation** (080): `Jobs:calculateQualityScore` multiplies five factors (skill headroom over the job's level, reliability, morale, starting kit condition from 045's `startCondition`, a random form roll) and rounds down, so 100 means all of them were at their best. A player-driven job is always 100. The completion reputation reward is the base reward times `getQualityReputationFactor` (full at 100, nothing at `REPUTATION_ZERO_QUALITY`, a loss below), so quality is set before the reward in `completeJob`. Skill reaches reputation only through quality, so don't scale the reward by skill again. Growth reads quality through `TheContractorStaff.getGrowthQualityMultiplier` (relative to an ordinary crew's 85).
- **Job events** (074): a random event about one job is rolled as the job completes, not daily. Register it with `chancePerJob` (a number, 0-1, no `ratePerPeriod`) and optional `minJobQuality`. `canTrigger(farmId, job)` gets the job (from the console, the framework passes the farm's latest completed job it accepts). `RandomEvents:onJobCompleted`, called last in `Jobs:completeJob`, lets at most one happen per job. The kettle, paid early and a worker stepping up live in `src/business/JobNews.lua` (`tc.JobNews`, no state, 073's `goodNews` inbox kind). A free stat point outside growth potential is `Staff:boostWorker`, and a job's invoice is `Finances:getInvoiceForJob`.
- **Road accidents** (079, `src/business/RoadAccident.lua`, `tc.RoadAccident`) are a job event (`chancePerJob`, no `minJobQuality`) with no state of their own: everything (scenario, the machine hit, fault, damage, claim, estimate) is rolled in `canTrigger` into the incident's data. Fault comes from the driver's tractor rating and the rig's worst wear (`getFaultChance`), never from job quality. A liability claim from anything other than a botch goes through `Claims:chargeClaim(farmId, amount, insured)`, which charges, records and loads the premium. A payout from someone else's insurer is `tcInsurancePayout` + `Finances:recordInsurancePayout`, with nothing on either claims history. `tcCompany outcome roadAccident <ours|theirs>` forces the next one's fault. A liability claim that isn't the job's botch goes on its logbook entry through `Claims:addToJobLog` (adds to a claim already there).
- **Spray drift complaints** (081, `src/business/SprayDrift.lua`, `tc.SprayDrift`) are a job event on hired herbicide jobs with no state of their own. Its `chancePerJob` is a **function** `(farmId, job)` (068 accepts a number or a function; `RandomEvents.resolveJobChance` reads either): the drift chance from the operator's crop care (`operationRating`) and the wind as the job completes (`windUpdater:getCurrentValues()`, m/s), plus a small chance of an unfounded complaint. Once a complaint's in, it's upheld with drift's share of that, so upheld overall is the drift chance. Certification can't clear anyone by itself, because every hired herbicide operator has it (054). A job with a pending 052 botch claim (`Claims:hasPendingClaimForJob`) gets none. `tcCompany outcome sprayDrift <upheld|cleared>` forces the next one's findings.
- **Worker poaching** (083, `src/business/Poaching.lua`, `tc.Poaching`) is a random event with no state of its own (incident data `{ workerId, workerName, offer, rivalName, messageId }`), rolled only in `WINDOW_PERIODS` (March–May, so even an offer left to expire has them gone by August). The target is weighted on market value squared; the offer is a full-month salary (unscaled, `$pay_`) 10–25% over the higher of pay and market value. Match → `PayReviews:setPay` and morale, always stays. Do nothing or expiry → a `decision` stage a day or two later, `getStayChance` (morale and 058's pay gap, 0–25%), else `Staff:announceLeaving(..., true)` with a month's notice. `Staff:retireWorker`/`releaseWorker` call `Poaching:onWorkerGone`, which closes an open offer.
- **Fly-tipping** (075, `src/business/FlyTipping.lua`, `tc.FlyTipping`) is a random event with no state of its own (incident data `{ fieldId }`, NPC fields only): it drops a pile of `TCDebris` (`src/util/TCDebris.lua`, hand-movable `MountableObject`s saved through vanilla's `ItemSystem`, every piece `TCDebris.MASS`, strappable with tension belts, each with its own map marker `TCDebrisHotspot` that follows it) 4-7 m in from the field's edge by its gate (`TCJoyriderRuts.planDumpSite`, with the van's ruts and a churned patch painted by `paintDumpSite` so it can be found) with `TCDebris.spawnPileAt` and offers a `flyTipping` job. That type is in `JOB_TYPES` but left out of `JOB_TYPE_KEYS`, so it's never generated or made by `tcJob`; it's priced and rewarded per piece (`rewardPerItem`/`reputationPerItem`, `createJobOnField`'s `itemCount`). The job holds its pieces' item uniqueIds (`job.debrisIds`, `debrisDisposed`, server-only, saved). Pieces disappear at a **disposal skip** (`src/placeables/PlaceableTCDisposalSkip.lua`, store item `xml/disposalSkip.xml`): trigger-based like vanilla's sell points (an engine trigger, a waiting list, `raiseActive` only while something's on it, never while held or strapped: `TCDebris.isHeld`/`getIsFree`), then `FlyTipping:disposeDebris` counts it and charges the tipping fee (`tcWasteDisposal`, `Finances:recordDisposal`). `Jobs:onJobDeclined` (a declined or expired offer) and `clearUpAfterJob` take whatever's left of a pile away. A new debris prop is a copied i3d with a dynamic root collision **re-saved in GIANTS Editor** (hand-editing the export isn't enough) in `i3d/debris/`, plus a `TCDebris.PROPS` entry.

A completed player-driven job keeps access for `TheContractorJobs.GRACE_PERIOD_MS` (real time, `job.graceRemainingMs`, counted down on every machine, streamed and saved) so the player can finish the strip the completion threshold leaves, and its `clearUpAfterJob` waits until then (`endGracePeriod`).
- **Who's on a job** (093): a player-driven job (`job:isPlayerDriven()`, no hired crew) keeps the nickname of the player who allocated it (`job.allocatedPlayerName`, from the request's connection through `TheContractorAllocation.getConnectionPlayerName`, saved and streamed). Show it with `job:getPlayerName()` (falls back to "A player"), never "You": in multiplayer that's wrong for everyone else. A job's status chip comes from `MenuContractor:getJobStatusChip(job)`, shared by the Calendar and the Job details dialog (`TCJobDetailsDialog`, rows from `MenuContractor:getJobDetailRows`).
- **Unallocating** (094): `Jobs:unallocateJob` (from `TCUnallocateJobEvent`, the Job details dialog's Unallocate, or `tcJob state <job> accepted`) puts an allocated or in-progress job back to `accepted`. The crew and kit go through `Jobs:releaseJobResources`, the part of a miss's release that leaves the field alone (`releaseMissedJobResources` adds `TCFieldPreparation.clearUpAfterJob`). The job keeps its field, bales and progress, and its saved, server-only `wasUnallocated` flag makes the next `allocateJob` skip `prepareFieldForJob` and the progress reset (and `TCHaulage.resumeDelivery` in place of `startDelivery`). - **Due job map markers** (088, `src/util/TCJobHotspots.lua`): vanilla's pulsing contract circle (`AbstractFieldMissionHotspot`) on the field of each local-farm job that's accepted, allocated or in progress with a `deadlineDay` no later than the month's last day. ## Build / test loop

In-game testing is the real check (load a save, check the menu, check `TheContractor.xml` after saving). Alongside it there are **unit tests** in `tests/`, run with `test.bat` (plain Lua 5.1, the default install path or `%LUA%`; `test.bat tests\test_foo.lua` runs one file). They load the real `src/` files against fake engine globals, so they check our logic, not our assumptions about vanilla:
- `tests/stubs.lua` — the fake FS25 globals; `stubs.install()` gives each test a fresh `world` with builders (`addVehicle`, `addStorage`) and records (farm stats, notifications, logs). `g_i18n` reads the real `languages/l10n_en.xml`, so a missing key fails. Extend it when code under test needs another engine call.
- `tests/fakes.lua` — fakes for mod modules a test doesn't load (Jobs, Dispatch, Logbook, ...) plus `world:addJob` building real `TheContractorJob`s.
- `tests/test_*.lua` — `test("name", function() ... end)` blocks with `assertEquals`/`assertNear`/`assertTrue`. Each file runs in its own process and stops at its first failure (no `pcall`, here too).
- **When a ticket's Outcome would cite a stubbed harness, write it as a `tests/test_*.lua` file instead** and run the whole suite before reporting back.

`.bat` scripts at repo root zip the mod and drop it into the local FS25 mods folder:
- `package.bat` — zips the repo (excluding `.git`, `.bat`, `.md`, `.vscode`, `.kiro`, `refs`, `docs`, `tickets`, `tests`) into `<modname>.zip`.
- `moveZip.bat` — moves the zip into `Documents/My Games/FarmingSimulator2025/mods/`, replacing any existing unpacked folder there.
- `moveDebug.bat` — same, but also unpacks the zip into a matching folder (for a debug/dev-console-friendly unpacked mod).

## Workflow with the user

- Tickets are built one at a time on request ("build 00N") — implement the full ticket, update its `Status` to `Done`, and append an `## Outcome` section noting anything that changed from the plan (deviations, sequencing shortcuts because a dependency ticket isn't done yet, etc.) before reporting back.
- **Console commands are subcommands of four groups** (`src/util/TCConsole.lua`): `tcWorker`, `tcJob`, `tcFinance`, `tcCompany`, plus `tcHelp`. Don't add a new top-level `addConsoleCommand`. Register a subcommand from the owning subsystem's static `registerConsoleCommands()` (called in `main.lua`'s loadMap) with `TCConsole.register(group, name, { args, description, serverOnly?, run(farmId, args) })`. `run` returns the text to print, or `false` for bad arguments. Take workers as `<worker>` via `TCConsole.findWorker` (id or name). They're not cheat-gated, on purpose: players use them to tailor their game. `serverOnly` defaults to true; set it false only for read-only lists.
- **Every console command is documented in `docs/commands.md`**, not the README (which just links to it). Put it under its group's heading (`##`), with the signature as a `###` heading, then what it does, its arguments and defaults, and a short example. Do this whenever you add a command, change its arguments or change what it prints (including extending an existing command for a new ticket), and remove the entry when you remove the command. Keep the in-game `args`/`description` in its `TCConsole.register` entry in step with it.
- Don't jump ahead to a later ticket's scope even if it'd be convenient (e.g. don't build real reputation logic while doing 006 — leave a placeholder and let 007 own it).
