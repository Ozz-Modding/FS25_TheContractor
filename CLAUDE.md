# The Contractor — CLAUDE.md

FS25 mod. Full design context lives in `BRIEF.md`; work is tracked ticket-by-ticket in `tickets/` (see `tickets/README.md` for the backlog, phase ordering, and cross-cutting decisions agreed during the initial grilling session). Always check a ticket's `Status` and `## Outcome` section before assuming its acceptance criteria describe the current code — outcomes note deviations.

## Conventions (established, don't relitigate)

Each entry is the rule and the trap, not the detail: the code and the ticket's Outcome have that.

### Foundations

- **State is farm-scoped**, not per-player (e.g. `Company.lua`'s `companyNames[farmId]`: a name there IS "has a company", don't add a flag beside it). Multiplayer has several farms, so never assume "the" farm: key off the right `farmId` (`g_currentMission:getFarmId()` for the local player's). No business ledger: money goes through `g_currentMission:addMoney(amount, farmId, moneyType, addChange, forceShowChange)`. Tax is out of scope (another mod).
- **Multiplayer is a hard requirement, not deferred.** Read `src/events/README.md` (event file shape, the `TCInitialClientStateEvent` aggregate, and its gotchas: no single-player broadcast loopback, never send raw node objects, defer object resolution during initial client state). Every new piece of mutable state needs an event; `src/events/TCCreateCompanyEvent.lua` is the "client requests, server validates and applies, broadcasts" template.
- **Save/load**: one `TheContractor.xml` per savegame (`TheContractor.SaveKey`), legacy XML API (`getXMLInt`/`setXMLString`/`hasXMLProperty`, not `xmlFile:getInt`). Each `src/business/` subsystem owns a `loadFromXMLFile`/`saveToXmlFile` pair, called from `main.lua`, and needs `writeInitialClientState`/`readInitialClientState` stubs even if empty.
- **Vehicle references** (`src/util/TCVehicleIds.lua`): in memory and on the wire a vehicle is its network object id; **the save stores `vehicle:getUniqueId()`**, since object ids change every load. Vehicles load after `loadMap`, so keep loaded uniqueIds in a holding field and convert them in the subsystem's `resolveSavedVehicles`, added to `TheContractor:resolveSavedVehicles`. On a client, wait until a vehicle has streamed in and synchronised before acting on it (`TCEquipmentVisibility`).
- **Logging goes through `TCLog`**, never `Logging`: `TCLog.info` is the detailed log (off by default, `tcLog` toggles it); `warning`/`xmlWarning`/`error` always log, so keep them for real problems.
- **No `pcall`** (or `xpcall`): ruled out for this mod. Nil-check the functions and fields you need instead.
- **Vanilla contracts are fully disabled**, not hidden (`src/util/DisableVanillaContracts.lua`), re-applied every `loadMap` because the Contracts tab's predicate closure is captured once at menu registration.

### Menu and UI

- **Menu**: one top-level page injected into the live `g_inGameMenu` at map load (`MenuContractor.registerInIngameMenu`, after RedTape/Courseplay); there's no declarative way. Tabs are one `TabbedMenuFrameElement` (`MenuContractor`) with `subCategoryPaging`. Gate tab content with `setText`/`setVisible`, never by removing tabs: reshuffling the indices at runtime is fragile. The Workshop tab (100) is the one exception, safe only because it's last.
- **The menu's enable predicate stays always `true`** and Actions is tab 1: "Create Company" has to be reachable before a company exists (`tickets/006-company-activation.md`). Don't "fix" it.
- **Action buttons go in the bottom button bar**, not in-page `Button`s: `self.menuButtonInfo[category]` entries, `getMenuButtonInfo()` for conditional ones, `setMenuButtonInfoDirty()` after a change. **The bar has a fixed number of slots and silently drops the rest**, so more actions than fit go behind one button opening an `OptionDialog` (`onClickManageWorker`).
- **Panel kit** (`src/gui/guiProfiles.xml`, `tickets/043-menu-visual-polish.md`): call `invalidateLayout()` on a `tc_detailRows` BoxLayout every time it's filled, or its rows don't render. Status goes in a chip (`setChip`), not `setTextColor`. **Every ListItem template must start with `<RoundCorner profile="tc_tableRowSurface"/>` and `<Bitmap profile="tc_tableRowAccent"/>`**, or rows have no background or selection. Element-level `with=` is ignored: anchors come from profiles. Mouse-over help goes through `TCTooltip` (one popup per page with its own layer, or text shows through); it's mouse only, so it may only add help, never something a gamepad player needs.
- **Dialogs**: `TextInputDialog.show(callback, target, defaultText, dialogPrompt, imePrompt, maxCharacters, confirmText)` (callback gets `(target, text, clickOk)`), `InfoDialog.show(text)`, `YesNoDialog.show(callback, target, text)`. In our own dialogs **never store state in `self.name`**: it's the GUI name `close()` closes by.
- **Icons**: `images/menuIcon.dds` is a placeholder the user swaps; don't design icons. `registerInIngameMenu`'s `iconImageSize` must match the file's real size (`GuiUtils.getUVs` assumes 1024 otherwise), so check it and the `uvs` rect when the icon changes.
- **Company logo and signs** (`src/util/TCCompanyLogo.lua`, `src/placeables/PlaceableTCLogoSign.lua`): local only by design, nothing saved or streamed; never read the save's modSettings slot on a joining client. A player's own logo shows only on their own farm's signs. Sign designs (a configuration built from `modSettings/.../signs/`) are single-player only, because configurations sync by index and each machine reads its own folder. `createSettingsFolder` runs as the scripts are sourced, not in `loadMap`, because the store items read `signs/` before the map loads. New sign i3ds come from `docs/tools/` (`docs/logo-sign-i3d.md`).
- **Settings** (`src/business/Settings.lua`) are server-wide: a `DEFINITIONS` entry, its id in `ITEMS`, `tc_setting_<id>`/`tc_toolTip_<id>` keys, and save, sync and the menu follow. A per-player display preference goes in `LOCAL_ITEMS` instead (never synced, saved in modSettings).

### Money

- **Money types: the full checklist, every time** (skipping step 4 silently breaks the Finances screen; it bit `tcCompanyCreation` and `tcAdvertising`):
  1. `FinanceStats.statNames`/`statNameToIndex` entry at module scope.
  2. `MoneyType.register(name, l10nKey)` + `MoneyType.LAST_ID = MoneyType.LAST_ID + 1` in the subsystem's `.new()` (once per `loadMap`, as RedTape does; not a bug to fix).
  3. The `l10nKey` text in `languages/l10n_en.xml`.
  4. A `finance_<name>` text too, and both keys in `TCI18NExtension.theContractorTexts`: vanilla's Finances screen looks `finance_<name>` up with no mod env, which only `TCI18NExtension` fixes.
- **Fixed business costs** (overheads, claims, fees, training, fines) are written at real UK rates and charged and shown through `Settings:scaleCost`, because job pay is far above UK rates (047). Pay (wages, bonuses, notice and redundancy, office salaries) is not scaled that way. Salaries are stored as full-month figures and go through `TheContractorStaff.scalePay` wherever they're charged or shown; an inbox arg showing one is `$pay_`, not `$money_`.
- **FS25_EconomyScale** (`src/util/TCEconomyScale.lua`): store amounts unscaled and apply its factor live. `Job:getPrice`/`getOfferedPrice`, `scaleCost` and `scalePay` already do; any other fixed amount goes through `TCEconomyScale.scale` when charged and shown. **Never scale anything read from a vanilla price getter** (EconomyScale already has). ADS prices use `TCEconomyScale.getADSFactor()`, never `getFactor` (except `ADS_Maintenance.getPartPrice` without a workshop, which EconomyScale never scales). Set a typed price with `job:setPrice`. History is fixed: `paymentAmount`, invoices and the logbook keep the amounts they had.
- **Job payment goes through `tc.Finances`** (`Finances:invoiceJob`, from `Jobs:completeJob`). Invoice outcomes are server-only. Anything that pays wages also calls `Finances:recordWages`.
- **Trade association and legal cover** (053) have no state of their own: read them with `Association:isMember`/`hasLegalCover`, and member perks (certificate discounts, the reputation bonus) go through `tc.Association`.
- **Recurring costs go through `tc.Overheads`** (`registerOverhead` on every machine at load, plus `tc_overhead_<key>`/`_desc` keys). Descriptions go through `string.format` with `descriptionAmounts`: put prices in as `%s`, never bare numbers, and write a literal percent as `%%`. Read cover with `isActive(farmId, key)`. A policy whose price depends on another uses the definition's `onActiveChanged` and `Overheads:repriceMidTerm` (053's legal cover).
- **Machinery insurance** (070): a definition can have cover `levels`. Its premium is a game price, so `unscaled = true`. An insurable event names its `peril`, stores `getCoverLevel(farmId, peril)` in its incident data on the day, and adds `getClaimStages(...)` to its stages; a new peril is a `PERILS` entry, not a new policy.

### Inbox and jobs

- **Asking the player something goes through Inbox messages** (`src/business/Inbox.lua`): `registerMessageKind` on every machine at load, `postMessage` on the server. Title and body are l10n keys with plain-value args (`$l10n_`, `$money_`, `$pay_`, `$days_<first>_<last>`, `$volume_` are formatted per client); at most 3 actions. **Any message offering a job uses a kind with `endsWithJob`** (the job in `payload.jobId`), so it goes with the job. An offer text that names the customer gets the name live through `TheContractorInbox.getCustomerNamedArgs` in the kind's `getArgs` (112), never as a posted arg.
- **Use `JOB_TYPES` flags, never job type names**, for behaviour (`deliversBales`, `deliveryOnly`, `noEquipment`, `offField`, `allocateOnAccept`, ...). Check "player only" with `TheContractorJobGeneration.isPlayerOnly(job)`, not `jobDef.playerOnly`. A type made only by its event stays out of `JOB_TYPE_KEYS`. An event that causes field work makes its job with `JobGeneration:createJobOnField`.
- **Name a job's place with `job:getLocationText()`** (or `getListFieldText` in a list), never the field directly.
- **Who's on a job**: show `job:getPlayerName()`, never "You" (wrong for everyone else in multiplayer). A job's status chip is `MenuContractor:getJobStatusChip(job)`.
- **Job field access** (`src/util/TCFieldAccess.lua`) is as strict as a vanilla contract: a new job type with ground work needs `workAreaTypes`, or nothing will work its field.
- **Relationships** (113): a farm's opinion of a customer changes only through `tc.Relationships` (server `adjust`). A new way an offer ends passes its `DECLINE_REASON` to `transitionJobState`. A farmer's pay habit is server-only: never stream or show it.
- **Job quality** (080): skill reaches reputation only through the quality score, so never scale a reward by skill again, and set quality before the reward in `completeJob`.
- **Unallocating** (094): anything new `allocateJob` sets up on a job, or holds for its crew, must be undone in `unallocateJob` and kept or redone on a resumed allocation (`wasUnallocated`).
- **Finished jobs are trimmed at save** (`Jobs:getJobsToSave`). **Anything new that holds a job id past the job's end must be added to `getHeldJobIds`**, and code looking up a finished job must cope with `getJob` returning nil.
- **Due job map markers** (`src/util/TCJobHotspots.lua`) re-read the jobs every second, so a new job path needs nothing there unless it changes what "due" means or the marker belongs somewhere other than the field (`getSpotPositions`).

### Staff

- **Worker names**: every new name goes through `TheContractorStaff.generateName(gender)`. The `nameStyle` setting saves the option's number, so a new style goes on the end of `NAME_STYLES` (plus `TCNames.STYLES`, `STYLE_ORDER` and a `tc_nameStyle_<key>` key).
- **Anything that gives a worker something to do checks `TheContractorWorkingHours.isAvailable(worker)`** (or `Staff:getAvailableWorkers`), not `worker:isIdle()` (097).
- **Sickness**: every new sickness goes through `Staff:makeWorkerSick` (it runs 055's inspection roll; its optional days override is how an injury sets its own). Clients don't hold `sickDaysRemaining`, so anything they show about it travels in the event (`TCWorkerStatusChangedEvent`).
- **Morale** (056): something that should please or upset staff calls `Morale:adjust` (a knock is scaled by 118's hidden temperament, which is server-only and never shown); read its effects through `TheContractorMorale`'s getters, and a rough patch through `isInRoughPatch`. Workers leave through `Staff:announceLeaving`/`retireWorker`. Anything that takes a worker off the roster also calls `PayReviews:removeMessagesFor` (`retireWorker`/`releaseWorker` already call 083's `Poaching:onWorkerGone`).
- **Pay** (058): `worker.salary` is real pay, only ever raised, through `PayReviews:setPay`. Market value is read live with `TheContractorPayReviews.getMarketValue`.
- **Certificates and training** (054): a job type that needs one names it as `certification` in `JOB_TYPES`; a new certificate is a `TheContractorTraining.CERTIFICATIONS` entry plus a `tc_cert_<key>` key. Every course length goes through `TheContractorTraining.scaleDays`. Anything reading `trainingCert` must allow for a trade course (092) with no assessment day.
- **Office staff** (057, 090) are people but not workers (no roster, allocation or skills). Their ids come from `Staff:takeWorkerId()`. Anything that pays or counts employees uses `Staff:getPayroll`/`getHeadcount`, not the roster. Anything that changes who ADS's workshop should see calls `TCADSWorkshop.refresh(farmId)`.
- **ADS workshop trades** (091) live on the worker and change only through `TCWorkerWorkshopEvent`. Our saves and ADS's API use ADS's role ids, but the player sees ADS's names for them (the diagnostician is "Electrician", the receptionist "Advisor"), so our l10n and console do too.
- **Editing a worker** (066) only through `Staff:editWorker`/`applyWorkerEdited`, and a farmer or the official (111) only through `Farmers:editPerson`/`applyPersonEdited`. Anything new that caches a person's look needs a reload hook there. Farmers' ids are their own, so a portrait of one passes a key (`MenuContractor.getPersonPortraitKey`), or it's taken for the worker with that id. Only one worker portrait may be visible at a time (render scenes share the world origin): a new place to show one moves the menu's one `TCWorkerPortrait` there with `setRender` (112), never makes a second. `WardrobeScreen`'s class methods can't be hooked (the element holds copies); see `src/gui/TCWardrobe.lua` for how the look is swapped in.
- **Standing spots** (065, 114): `TCIdleStaff.assign` and `TCYardFarmers` must give every machine the same answer, so feed them synced state only and never `math.random`. A yard's spots for that are the server's synced list (`Yards:getSpots`), never `findSpots` (a client's differs). `TCIdleStaff.hash` is affine, so raw it barely changes from day to day: mix it as 114's `hashSpot` does. A spot kept for named staff (120) takes nobody else: anything new that puts people on standing spots goes through `assign`'s `reservedFor`.

### Equipment

- **Parking** (062): equipment back from a job is never revealed where it stood; it goes to `tc.Parking:returnVehicles`. A vehicle is in a cooldown or the parking queue, never both, so anything that takes a machine out again calls `removeVehicles` first, and `Cooldown:releaseVehicles` takes one machine out of a running cooldown. Slot types never fall back to another type; a filter only narrows. New placeables point their `<brush><tab>` at `contractor`. **Hooking `ConstructionScreen.onOpen`/`onClose` on the class does nothing** (the element holds copies): `TCParking.installConstructionScreenHook` shows how. A regenerated (inline-mesh) i3d must be re-saved in GIANTS Editor to get its `.shapes` file (`docs/parking-slot-i3d.md`).
- **Selling busy equipment**: `TCVehicleLock` refuses it at `SellVehicleEvent.run`. Never call `Enterable:setIsTabbable` for a temporary state (vanilla saves it). **Never hook `getIsInUse`** for job or courtesy vehicles: our own dispatch's `AIJob:getIsStartable` checks it and would refuse them.
- **Machines to keep out of our lists**: check `tc.Theft:isStolen(vehicleId)` and `TheContractorRepairContracts.isContractVehicle(vehicle)` in any new list of the farm's vehicles. A courtesy vehicle is `MISSION` state, so `propertyState == OWNED` skips it; vanilla only lets a MISSION vehicle's work areas work on mission fields, hence 071's `WorkArea.getIsAccessibleAtWorldPosition` patch.
- **Lying a vehicle down**: physics won't keep any vehicle on its side, so freeze it as 105's `TheContractorTippedTrailer.setLying` does (out of physics as a vehicle, components kinematic, so vanilla never builds wheel shapes on a kinematic body).
- **Job diesel and supplies** come from the farm's own stock (063, 032). **All ADS stock access goes through `TCADSStock`**: one capability flag per feature, a nil-checked lookup, a test that removes it, and a missing function hides only what needs it. The menu never calls ADS directly.
- **Vanilla AI helpers**: contract jobs' notifications are dropped and their restart after a load is ours (`src/util/TCAINotifications.lua`, `TCAIRestart.lua`); a staff driver's are vanilla's with the worker's name.

### ADS (FS25_AdvancedDamageSystem)

- **Everything ADS goes through our wrappers** (`TCADSRepairContracts`, `TCADSWorkshop`, `TCADSStock`), found by their functions and nil-checked; ADS globals through `TheContractorDrivers.getModEnv`. Read `docs/ads-repair-contracts.md`, `docs/ads-repair-contracts-revised.md` and ADS's `docs/ADS_RepairContracts_API_1.md` before touching repair contracts.
- **Logbook** (060): something new that belongs in a job's record is stored on the server's pending data for that job (`onWorkStarted`/`onArrived`/`onSuppliesLoaded`) and copied in by `buildJobEntry`. Show vehicle condition with `getChangeRows`/`getStateRows`, never by assuming vanilla's or ADS's model.
- **Show only what the player knows** (099, at the ADS author's request): never put ADS's live condition, hidden faults or which job caused a fault on screen, and show no wear cost for an ADS vehicle. Logbook condition goes through `TCVehicleCondition`.
- **Repair contracts** (100-102): nothing can be done to a customer's machine until a price is agreed (`TCADSRepairContracts.authorize`). **Never price from `quote.price`** (the dealer's whole bill), and never show a total before the job's inspected (ADS's totals include hidden faults). Missing kit only warns. A customer's machine is never locked for driving. Workshops are told about these machines through `isWorkableVehicle`/`addWorkableVehiclesInRange` (vanilla's and the service vehicle mods' in `src/util/TCServiceVehicleMods.lua`); **never make `getShowInVehiclesOverview` true for them**. Tell a field breakdown (101) apart with `isBreakdownJob` (an arrival by its `kind`), never by having a field: it can be in a farmer's yard (123). Its kit is the field kit, not the workshop's.
- **Farmer favours** (116): a favour is a workshop job with a customer (`isFavourJob`, the JOB_TYPES `favour` flag), about a part a farm can stock and fit by hand: only ADS's graded parts (`TCADSRepairContracts.getStockParts`), never part names in our code and never parts made for one model. A farmer's machines (121's fleet, `TheContractorFarmerFleet`) are records on the farmer, spawned through 100's queue, never vehicles kept on the map: anything new that brings one out skips it while `isMachineOut`, brings its attachment (`getAttachmentArrival`, `getFootprint`), and only ever adds machines (ids are never reused; 122's edit changes a model under the same id). Clients hold only each machine's id, role, model and `attachedTo` (122): seed, age and fitted parts are server-only, and any change to a fleet is sent in `TCFarmerFleetEvent`. A field breakdown (101) can carry a `farmerId` and `machineId` too, so tell a favour by `isFavourJob`, never by those.

### Random events

- **The framework** (068, `src/business/RandomEvents.lua`): register on every machine in `loadMap` with `registerEventType`. Odds are **per month** (`ratePerPeriod`), per completed job (`chancePerJob`, a number or a function of the job), or per spell of bad weather (`chancePerStorm`); stage waits are in months. **Never write an event's odds or waits in days.** `triggerHours` holds a hit for a time of day. `canTrigger` returns flat number/string/boolean data (that's what's saved and synced) or nil. **An event's console needs go on its definition (`console = { ... }`), never a new `tcCompany` subcommand.** Messages, notices and money come from the event's own stages.
- **What each event type adds** that others must respect:
  - Theft (069): `isStolen` checks (above); ADS anti-theft through `TheContractorTheft.hasAntiTheft`.
  - Good news (073): a story is a `STORIES` entry plus its keys; anything needing more mechanics is its own event type.
  - Road accidents (079) and other non-botch liability claims go through `Claims:chargeClaim` and `Claims:addToJobLog`.
  - Spilt crop (106): check `job.spill ~= nil`. Its site is the farm's land for shovels, tipping and levelers; any new tool that works heaps needs the same hook.
  - Fly-tipping (075): a new debris prop is a copied i3d with a dynamic root collision **re-saved in GIANTS Editor** (hand-editing the export isn't enough).
  - Bales to a yard (124): a job that borrows a farmer's machine holds it in `isMachineOut` from its offer, and brings it out as a loan arrival on 100's queue (`queueLoanArrival`: no ADS, never saved, sent for again after a load).
  - Fallen tree (107): put a felled tree down with `g_treePlantManager:plantTree`, never `loadTreeTrunk` (it sends clients nothing), and queue the cut on vanilla's `loadTreeTrunkDatas` after a delay so clients have the tree first. Keep a shape across saves with `getSaveableSplitShapeId`. Anything that leaves trees or logs on land the farm can't use needs the same cut permission hook (`SplitShapeManager.getIsShapeCutAllowed`).

## Build / test loop

In-game testing is the real check (load a save, check the menu, check `TheContractor.xml` after saving). Alongside it there are **unit tests** in `tests/`, run with `test.bat` (plain Lua 5.1, the default install path or `%LUA%`; `test.bat tests\test_foo.lua` runs one file). They load the real `src/` files against fake engine globals, so they check our logic, not our assumptions about vanilla:
- `tests/stubs.lua` — the fake FS25 globals; `stubs.install()` gives each test a fresh `world` with builders (`addVehicle`, `addStorage`) and records (farm stats, notifications, logs). `g_i18n` reads the real `languages/l10n_en.xml`, so a missing key fails. Extend it when code under test needs another engine call.
- `tests/fakes.lua` — fakes for mod modules a test doesn't load (Jobs, Dispatch, Logbook, ...) plus `world:addJob` building real `TheContractorJob`s.
- `tests/test_*.lua` — `test("name", function() ... end)` blocks with `assertEquals`/`assertNear`/`assertTrue`. Each file runs in its own process and stops at its first failure (no `pcall`, here too).
- **When a ticket's Outcome would cite a stubbed harness, write it as a `tests/test_*.lua` file instead** and run the whole suite before reporting back.
- **Tests are functional: never assert player-facing text**, as a literal or against `getText(...)` (rendered messages, notifications, notices, console output, summaries). Assert the keys, args and state behind it; if the data only exists inside a formatter, split it out (`Holidays.getOthersOff`).

`.bat` scripts at repo root zip the mod and drop it into the local FS25 mods folder:
- `package.bat` — zips the repo (excluding `.git`, `.bat`, `.md`, `.vscode`, `.kiro`, `refs`, `docs`, `tickets`, `tests`) into `<modname>.zip`.
- `moveZip.bat` — moves the zip into `Documents/My Games/FarmingSimulator2025/mods/`, replacing any existing unpacked folder there.
- `moveDebug.bat` — same, but also unpacks the zip into a matching folder (for a debug/dev-console-friendly unpacked mod).

## Workflow with the user

- Tickets are built one at a time on request ("build 00N") — implement the full ticket, update its `Status` to `Done`, and append an `## Outcome` section noting anything that changed from the plan (deviations, sequencing shortcuts because a dependency ticket isn't done yet, etc.) before reporting back.
- **Console commands are subcommands of four groups** (`src/util/TCConsole.lua`): `tcWorker`, `tcJob`, `tcFinance`, `tcCompany`, plus `tcHelp` and `tcLog`. Don't add a new top-level `addConsoleCommand`. Register a subcommand from the owning subsystem's static `registerConsoleCommands()` (called in `main.lua`'s loadMap) with `TCConsole.register(group, name, { args, description, serverOnly?, run(farmId, args) })`. `run` returns the text to print, or `false` for bad arguments. Take workers as `<worker>` via `TCConsole.findWorker` (id or name). They're not cheat-gated, on purpose: players use them to tailor their game. `serverOnly` defaults to true; set it false only for read-only lists.
- **Every console command is documented in `docs/commands.md`**, not the README (which just links to it). Put it under its group's heading (`##`), with the signature as a `###` heading, then what it does, its arguments and defaults, and a short example. Do this whenever you add a command, change its arguments or change what it prints (including extending an existing command for a new ticket), and remove the entry when you remove the command. Keep the in-game `args`/`description` in its `TCConsole.register` entry in step with it.
- Don't jump ahead to a later ticket's scope even if it'd be convenient (e.g. don't build real reputation logic while doing 006 — leave a placeholder and let 007 own it).
